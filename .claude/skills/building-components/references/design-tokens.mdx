One of the core foundations of modern component libraries lies in their thoughtful approach to styling. Rather than hardcoding colors or creating rigid class systems, we can employ a semantic naming convention that separates the concerns of theme, context, and usage.

This semantic naming convention is known as design tokens. This architectural decision creates a maintainable, flexible system that scales beautifully across applications.

## The Philosophy of Semantic CSS Variables

Traditional CSS approaches often couple color values directly to their usage contexts, creating brittle systems that are difficult to maintain. Design tokens take a different approach by creating layers of abstraction that separate what something is from how it looks.

## Understanding the Variable Architecture

Let's examine how we can structure our CSS variables to create this flexible system:

```css title="globals.css (token layer only)"
/* Keep the stack template's existing Tailwind import and @source declarations.
   Do not copy a new import from a reference file: each stack profile owns which
   application roots Tailwind is allowed to scan. */

@custom-variant dark (&:is(.dark *));

@theme inline {
  --color-background: var(--background);
  --color-foreground: var(--foreground);
  --color-primary: var(--primary);
  --color-primary-foreground: var(--primary-foreground);
}

:root {
  --background: oklch(1 0 0);
  --foreground: oklch(0.145 0 0);
  --primary: oklch(0.205 0 0);
  --primary-foreground: oklch(0.985 0 0);
}

.dark {
  --background: oklch(0.145 0 0);
  --foreground: oklch(0.985 0 0);
  --primary: oklch(0.922 0 0);
  --primary-foreground: oklch(0.205 0 0);
}
```


## Tailwind v4: tokens and source scope are different contracts

The generated stack profile owns Tailwind's **source roots**. Its stylesheet deliberately limits scanning to application
files; `.claude/`, `.workflow/`, specs and reference Markdown must never become production CSS inputs. Preserve the
existing `source(none)` / `@source` declarations instead of re-enabling repository-wide discovery.

Use the narrowest token mechanism that expresses the contract:

- ordinary contractual CSS variables that do not need Tailwind utilities belong in `:root`;
- variables that define Tailwind theme utilities belong in `@theme`;
- a contractual theme variable that must exist in emitted CSS even before a class references it belongs in
  `@theme static`;
- a theme mapping whose value references another CSS variable belongs in `@theme inline` when inline resolution is
  required.

Do not use a documentation example as the only consumer that keeps a token alive. Final verification happens against the
clean application state after temporary probes are removed.

In the above example, we have four design tokens:

- `--background`, which is used for background colors (primarily the background of the page)
- `--foreground`, which is used for foreground colors (the general text color)
- `--primary`, which is used for primary colors (the main color of the brand)
- `--primary-foreground`, which is used for primary foreground colors (the text color, as seen against the primary color)
