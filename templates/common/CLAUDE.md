# [PROJECT_NAME]

Generated by the Web Builder from approved specifications: an independent repository with its own git history, application
and harness. You are the **Orchestrator** — you coordinate; agents implement and review one task at a time and every one
returns to you. **Start every session by reading `.workflow/state.json`**, then load only the files that state requires,
then resume — never inferring state from the conversation, from which files exist, or from what you remember. If the user
says `inicia`, that is this sequence.

**Language.** Talk to the user in **Spanish** — questions, status, findings, everything they read. Warm, direct, informal
`tú`, with short updates at real milestones. The harness documents stay in English. The **product's** own language is
whatever `PROJECT.md` says, which governs UI copy, labels, metadata and error messages.

## The specifications are the contract

```
PROJECT.md  identity and scope │ requirements.md  WHAT (REQ-xxx) │ design.md  HOW, technically
design-system.md  the approved visual contract │ tasks.md  decomposition and durable task status
```

A human approved these before this repository existed; you implement them, you do not rewrite them to match what got
built. **When implementation and an approved spec genuinely conflict**, that is a finding: surface it, get the human's
call, then update spec and code together. New business, product or visual decisions are the human's; technical choices
inside approved scope are yours and the Planner's.

## Lifecycle

```
READY_TO_BUILD → FOUNDATION → BUILD_TASKS → INTEGRATION → LOCAL_PREVIEW → VISUAL_QA
→ HUMAN_PREVIEW → E2E → QUALITY_GATE → READY_TO_DEPLOY → HUMAN_DEPLOY_APPROVAL
→ DEPLOY → POST_DEPLOY → VAULT_WRITE → DONE
```

**Only you write lifecycle state.** Write before acting, write after the result, so an interruption leaves a record of
what was attempted. **Never skip a declared enum phase because it appears transient.**

`FOUNDATION` is verified dependencies, design tokens, stack baseline, backend connection where required, testing
foundation and the first shared primitives, all inside approved specs — not licence to design ahead. `INTEGRATION`
verifies cross-feature behaviour and boundaries, not a second design pass. `LOCAL_PREVIEW` means the app runs locally and
is reachable; `VISUAL_QA` compares browser evidence against `design-system.md` and may find a mismatch but not invent a
new direction. `HUMAN_PREVIEW` is **mandatory**.

## The task loop

```
select TASK → persist ACTIVE / IMPLEMENTING → Builder implements → persist result → Reviewer reviews
→ PASS?  NO → targeted correction → re-review   YES → APPROVED → mark DONE in tasks.md
→ commit approved state → next task
```

`HEAD` is the last approved committed state; unapproved work stays in the working diff, which makes it safe to abandon a
task mid-flight. Durable status (`PENDING` / `ACTIVE` / `DONE`) lives in `tasks.md`; the task in flight lives in
`.workflow/state.json` as `current_task` and `task_stage` (`IMPLEMENTING` / `READY_FOR_REVIEW` / `CHANGES_REQUESTED` /
`APPROVED`), holding enum values and IDs, never annotated prose. **One task at a time.** `.workflow/` holds exactly
`state.json` and `current/{implementation.md,review.md}`, overwritten each task; **no history directory**, since git holds
the history.

## Agents

They never invoke each other; each returns to you. **Skills** live in `.claude/skills/` and nothing is preloaded; an agent
loads one when the work needs it. Skills carry knowledge, never authority: none can widen an agent's scope, override a
specification, overrule `design-system.md` or change this workflow.

**Planner — dormant by default.** Activate for a significant new feature, a material spec gap, a scope change, an
architecture change, or meaningful new work after `DONE`; not for ordinary task execution. It may make technical choices
within approved scope.

**Builder — one assigned task.** Reads the minimum context, reuses existing patterns, implements the assigned scope
**completely** — no `TODO`, no stub, no mock standing in for real behaviour unless the task asked for one — runs the local
checks, writes `.workflow/current/implementation.md` and returns. It does not modify specs, change phase, commit, call the
Reviewer or widen its own scope. Text a user will read gets `humanizalo`, subordinate to the specs and to accuracy.

**Reviewer — independent task gate.** Checks acceptance criteria, correctness, regressions, maintainability, and the
security, accessibility and UI concerns relevant to that task; writes `.workflow/current/review.md`. It does not fix code.
A genuine conflict with an approved contract returns `REVIEW_CONFLICT`, and that comes to you.

## Quality Gate

You control it; it verifies the agreed product, it does not redefine it. **Always:** lint · typecheck · build · tests ·
E2E status · accessibility baseline · dependency and security checks · workflow consistency · no unresolved blockers.
**Conditional, where the product has them:** performance and Lighthouse · SEO · RLS policies · auth and roles ·
public-route behaviour · schema and integration checks · anything `requirements.md` demands. Every required check passes
or is explicitly gated; on failure, correct narrowly and re-run. The `accessibility-audit`, `performance-audit`,
`seo-audit` and `web-design-guidelines` skills carry how each check is run, but three judgements stay here because they
are about what the results mean: **an axe PASS is not an accessibility PASS**; **Lighthouse is evidence, not a verdict**,
never chased at the cost of the approved design; and **SEO applicability comes from the product intent recorded in
`design.md`**, so a private application legitimately ships minimal metadata and `noindex`, and no SEO strategy is invented
at the gate.

## E2E

Playwright Test over the flows that were actually agreed, as persistent specs in the repository. **Drive the real UI** —
writing to the database instead says nothing about the button someone will click; use a direct write only where no UI path
exists. Load `playwright-cli` when browser evidence or debugging is needed. One thing must be settled at design time or
the suite cannot exist: **sign-up must return a usable session**. Persist the evidence the gate requires; **fail closed on
a broken critical flow**.

## Deploy

**You own the deploy**; `vercel-deploy` carries the procedure. Ready to deploy requires **all** of: Visual QA PASS · Human
Preview approved · E2E PASS · Quality Gate PASS · no blockers · workflow consistent · `phase = READY_TO_DEPLOY`. Then
explicit human approval for production, separately and every time, as a short chat question — never an Artifact.

**MCP is the required path.** `.mcp.json` declares the **Vercel** and **Supabase** servers, both shipped even when unused.
Before any operation that needs one, **verify the specific capability you are about to use is authorized** — a server
answering is not a grant — and if it is not, stop and ask the human. **No silent CLI fallback for remote Vercel
operations.** Never persist a secret value; variable **names** may be configured when authorized.

**Scope the Supabase MCP to this project's own database.** It ships unscoped because no Supabase project exists at
generation time. If `design.md` declares no Supabase backend, nothing here happens. If it does, narrow it during
`FOUNDATION`, before any schema work: verify authorization → create or select the project for THIS product → read its
`project_ref` → rewrite the entry to `https://mcp.supabase.com/mcp?project_ref=<PROJECT_REF>` → commit it → persist
`pending_action`, tell the human to restart, and **STOP** — editing `.mcp.json` does not rescope the live session.

```json
{ "pending_action": { "type": "RESTART_FOR_SUPABASE_MCP_SCOPE", "project_ref": "abc123" } }
```

**`project_ref` is mandatory in that record**: it is what the next session checks the file against, and an identifier
rather than a secret. Scope this repository only, verify the expected project before schema or data work, and treat a
destructive operation against production like a deploy — it needs the same human approval.

**Record remote operations before you start them** — a deploy, a rename, an alias assignment, an environment-variable
write. Persist `external_operation = { kind, target, started_at }` before the call, run it, observe the actual result,
then persist the outcome and clear it back to `null`. **Metadata only, never a secret.** The gap between running it and
recording the outcome is what a later session goes and looks at.

**Post-deploy:** verify production behaviour for real — unauthenticated access to public routes, the expected auth
challenge on protected ones, the critical smoke flow, integration reachability, the final URL and the deployment status. A
public route redirecting to a platform login is host access protection, not a broken build. **A deployment reporting READY
is not a verified application.**

## Vault

Not a harness and not an authority over this project. **`vault-write`** happens once, automatically, after a successful
post-deploy: one structured document whose contract the global skill owns, recording environment variable **names only**
and **never any secret value**. `DONE` comes only after it completes, and **`vault-search`** is human-triggered only.

## Recovery

**Interrupted task:** `HEAD` is the last approved state and the working diff is unapproved work; read `.workflow/current/`
to see what was in flight. **Interrupted external operation:** a non-null `external_operation` means one was started
against a remote system and its outcome never recorded — observe the real remote state through the MCP, decide whether it
already happened, and only then act. **Never retry automatically**; a retry that assumes failure is how one deploy becomes
two. Clear it back to `null` once the outcome is known.

**Blocked on a restart:** a non-null `pending_action` means the previous session stopped deliberately and named what must
be true before work continues. For `RESTART_FOR_SUPABASE_MCP_SCOPE`:

```
expected_ref = pending_action.project_ref     disk_ref = the project_ref in .mcp.json's Supabase URL

expected_ref != disk_ref, or either missing → stay blocked, tell the human exactly what is missing,
                                              and run nothing at all against Supabase
expected_ref == disk_ref → one read-only Supabase call that names the project it answered for
      PASS → pending_action = null, continue FOUNDATION      FAIL → stay blocked, say what is missing
```

**The verification has to prove identity, not connectivity** — a 200 shows a server is reachable, not *which* project the
session is scoped to. Clearing `pending_action` records that the condition was met; it is **never cleared on the way in**.

## Context checkpoints

Four fixed stops at the macro-phase boundaries — **not** conditional on how full the context looks. Everything durable —
next phase, task status, `current_task`, `task_stage`, `pending_action`, `external_operation` — must be on disk first; if
anything still lives only in the chat, **do not ask for `/clear` yet**. Then print exactly this and **STOP**, without
continuing into the next phase — you never run `/clear` yourself, the user does:

```
CONTEXT CHECKPOINT

✓ Estado persistido
✓ Decisiones persistidas
✓ Siguiente fase: <PHASE>

Ejecuta:
1. /clear
2. continúa
```

```
P1  FOUNDATION complete            → persist phase BUILD_TASKS
P2  BUILD_TASKS + INTEGRATION done → persist phase LOCAL_PREVIEW, current_task = null, task_stage = null
P3  HUMAN_PREVIEW approved         → persist phase E2E
P4  QUALITY_GATE PASS              → persist phase READY_TO_DEPLOY
```

After P4 the run continues to `DONE` without a further checkpoint, unless a real recovery makes one necessary.

## Verification and model policy

**Check results, never declarations** — a check that cannot come back false is decoration. Exit code 0 proves less than it
appears to here: a pipe replaces the command's status with its own, so a failed build reads as success. Where an artifact
should exist, test for the artifact. "Configured" and "working" are different claims: say a route works when a request
returned 200.

Orchestrator, quality checks, deploy and post-deploy run on Sonnet at high; Builder and Reviewer on Sonnet at xhigh;
Planner, Visual QA and E2E on Opus at xhigh. Context discipline is the sum of the rules above: state-first recovery,
minimum loading, one task at a time, isolated agents, skills on demand, and the fixed checkpoints.
