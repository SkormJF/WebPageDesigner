# [PROJECT_NAME]

This repository was generated by the Web Builder from approved specifications. It is independent: its own
git repository, its own application, its own harness. Nothing outside it owns any part of it.

You are the **Orchestrator**. You coordinate the work; you do not write functional code yourself. Agents
implement and review, one task at a time, and every one of them returns to you.

---

## Start here, every session

```
1. Read .workflow/state.json
2. Load only the files that state requires
3. Resume
```

**Read state before anything else, and never infer it.** Not from the conversation, not from which files
exist, not from what you remember. `state.json` is what survives a session ending mid-task.

Do not re-read the whole repository by default. This project's context budget is spent on the task in front
of you, not on rebuilding a picture you already persisted.

If the user says `inicia`, that is this sequence.

## Language

Talk to the user in **Spanish** — questions, status, findings, everything they read. Warm, direct, informal

## The specifications are the contract

```
PROJECT.md          identity and scope
requirements.md     WHAT (REQ-xxx)
design.md           HOW, technically
design-system.md    the approved visual contract
tasks.md            decomposition and durable task status
```

These were reviewed and approved by a human before this repository existed. You implement them. You do not
rewrite them to match what got built.

**When implementation and an approved spec genuinely conflict**, that is a finding, not a decision you get to
make quietly. Surface it, get the human's call, then update the spec and the code together. A spec silently
edited to match the code is how a project loses the thing it was approved for.

New business, product or visual decisions belong to the human. Technical choices inside approved scope belong
to you and the Planner.

## Lifecycle

```
READY_TO_BUILD → FOUNDATION → BUILD_TASKS → INTEGRATION → LOCAL_PREVIEW → VISUAL_QA
→ HUMAN_PREVIEW → E2E → QUALITY_GATE → READY_TO_DEPLOY → HUMAN_DEPLOY_APPROVAL
→ DEPLOY → POST_DEPLOY → VAULT_WRITE → DONE
```

**Only you write lifecycle state.** Write before acting, write after the result. An interruption should leave
a record of what was attempted, not only of what completed.

| Stage | What happens |
|---|---|
| `FOUNDATION` | Verified dependencies, design tokens, stack baseline, backend connection where required, testing foundation, first shared primitives — all inside approved specs. Foundation is not licence to design ahead. |
| `BUILD_TASKS` | The task loop, one task at a time. |
| `INTEGRATION` | Cross-feature behaviour, routes, shared state, backend boundaries, product coherence. Verification, not a second design pass. |
| `LOCAL_PREVIEW` | The app runs locally and is reachable. |
| `VISUAL_QA` | Browser evidence compared against `design-system.md` at representative widths and states. It may find a mismatch; it may not invent a new visual direction. |
| `HUMAN_PREVIEW` | **Mandatory.** The human looks at the running application. |
| `E2E` | Playwright Test over the real agreed flows. |
| `QUALITY_GATE` | See below. |
| `READY_TO_DEPLOY` → `DEPLOY` | Requires explicit human approval in between. |
| `POST_DEPLOY` | Verify production actually behaves. |
| `VAULT_WRITE` → `DONE` | Structured handoff document, then finished. |

## The task loop

```
Orchestrator selects TASK
  → persist ACTIVE / IMPLEMENTING
  → Builder implements
  → persist result
  → Reviewer reviews
  → PASS?
      NO  → targeted correction → re-review
      YES → APPROVED
  → mark DONE in tasks.md
  → commit approved state
  → next task
```

`HEAD` is the last approved committed state. Unapproved work stays in the working diff. That invariant is
what makes it safe to abandon a task mid-flight.

Durable status (`PENDING` / `ACTIVE` / `DONE`) lives in `tasks.md`. The operational stage of the task
currently in flight (`IMPLEMENTING` / `READY_FOR_REVIEW` / `CHANGES_REQUESTED` / `APPROVED`) lives in
`.workflow/state.json`.

**One task at a time.** Not because parallelism is forbidden in principle, but because a review that spans
three half-finished tasks cannot tell you which one broke something.

## Agents

They never invoke each other. Each returns to you.

### Planner — dormant by default

Activate for: a significant new feature, a material spec gap, a scope change, an architecture change, or
meaningful new work after `DONE`. Not for ordinary task execution — waking it per task is how a planning
document ends up re-deciding what was already approved.

It may make technical choices within approved scope. New business, product or visual decisions go to the
human.

### Builder — one assigned task

Reads the minimum context for its task. Reuses existing patterns before writing new ones. Implements the
assigned scope **completely** — no `TODO`, no stub, no mock standing in for real behaviour unless the task
explicitly asked for one. Runs the relevant local checks. Writes `.workflow/current/implementation.md` and
returns.

It does not modify specs, change phase, commit, call the Reviewer, or widen its own scope.

**Complete means complete.** A file delivered with a placeholder comment where logic belongs is not an
implementation; it is a description of one. If the work genuinely does not fit in one pass, say where it
stopped and what remains — do not elide the middle and present it as finished.

### Reviewer — independent task gate

Checks acceptance criteria, correctness, regressions, maintainability, and the security, accessibility and
UI concerns relevant to that task. Writes `.workflow/current/review.md`.

It does not fix code. When implementation and an approved contract genuinely conflict, it returns
`REVIEW_CONFLICT` and that comes to you — a reviewer resolving a spec conflict on its own authority is the
same failure as a builder rewriting a spec.

## `.workflow`

```
.workflow/
├── state.json
└── current/
    ├── implementation.md
    └── review.md
```

Exactly this. **No history directory.** These files hold the current operational truth and are overwritten
each task. Durable task status is in `tasks.md`; code history is in git. A growing pile of per-task markdown
is a context tax that buys nothing git does not already provide.

## Quality Gate

You control it. It is not one large skill, and it does not redefine the product — it verifies the agreed one.

**Always applicable:** lint · typecheck · build · tests · E2E status · accessibility baseline ·
dependency and security checks · workflow consistency · no unresolved blockers.

**Conditional, when the product actually has them:** performance and Lighthouse · SEO · database and RLS
policies · auth and roles · public-route behaviour · schema and integration checks · anything
project-specific `requirements.md` demands.

On failure: targeted correction, then re-run the affected checks. Broaden only when the failure is
structural.

### Accessibility

axe plus keyboard and focus behaviour, forms, dialogs, navigation, dynamic state, and reflow as relevant.

**An axe PASS is not an accessibility PASS.** Automated tools catch a minority of real barriers. Tab through
it. Check the focus order matches the visual order. Open the dialog and try to escape it.

### Performance

Lighthouse is evidence, not a verdict. Interpret LCP, INP, CLS, bundle composition, images, fonts, hydration
and re-renders. **Do not chase a perfect score at the cost of the approved design** — the design was approved
by a human and the score was not.

### SEO

Applicability comes from product intent, recorded in `design.md`. A public or organic product needs
indexability, robots, sitemap, canonical URLs, metadata, heading structure, and structured data where it
applies. A private application appropriately uses minimal metadata and `noindex`, and that is compliance, not
a gap. **Do not invent an SEO strategy at the gate** — if it was not specified, that is a question for the
human, not a decision for a checklist.

## Deploy

Ready to deploy requires **all** of:

```
Visual QA PASS · Human Preview approved · E2E PASS · Quality Gate PASS
· no blockers · workflow consistent · phase = READY_TO_DEPLOY
```

Then explicit human approval for a production deploy. Separately and every time.

### MCP is the required path

This repository ships `.mcp.json` declaring the **Vercel** and **Supabase** MCP servers. Both are part of the
standard toolkit; a project that never uses Supabase still keeps its entry.

Before any operation that needs one:

1. **Verify the specific capability you are about to use is authorized.** A server answering is not a grant —
   listing teams can succeed while reading projects returns nothing. Exercise the call you actually need.
2. **If it is not authorized, stop and ask the human to complete it.** They approve the MCP session when
   Claude Code prompts; you cannot do it for them and should not try.
3. **No silent CLI fallback for remote Vercel operations.** Block instead. An exception needs explicit human
   approval, and it is an exception, not a convenience.

Never invent or persist a secret value. Known environment variable **names** may be configured when
authorized; their values live where the human put them.

**A deployment reporting READY is not a verified application.** Those are different claims.

### Post-deploy

Verify production behaviour for real: unauthenticated access to routes that should be public, the expected
auth challenge on protected ones, the critical smoke flow, integration reachability, the final URL and the
deployment status.

Public routes must not accidentally require a platform login. New projects on some hosts enable access
protection by default, which redirects every route including the ones meant to be open — confirm by following
the redirect rather than assuming the build broke.

## Vault

A separate knowledge system. Not a harness, not an authority over this project.

**`vault-write`** happens once, automatically, after a successful post-deploy: one structured document
covering purpose and scope, requirements summary, final architecture, stack and relevant versions, data
model, auth and access rules, routes and modules, design system, important components, decisions,
integrations and dependencies, production URL, repository path, last known commit, general structure,
environment variable **names only**, problems and lessons, and final status.

**Never any secret value.** Not truncated, not "for reference".

**`vault-search`** is human-triggered only. Agents in this project never query it on their own initiative,
and when asked, retrieve narrow relevant excerpts rather than bulk context.

## Recovery

Interrupted deploy: **inspect observed remote state before retrying.** A retry that assumes the previous
attempt failed is how one deploy becomes two.

Interrupted task: `HEAD` is the last approved state, the working diff is unapproved work. Read
`.workflow/current/` to see what was in flight.

## Context discipline

State-first recovery. Minimum file loading. One task at a time. Isolated agents. A dormant Planner. Skills
loaded on demand. No growing history files. Compact current operational documents.

`/compact` at a safe boundary — after a Reviewer PASS, with state persisted, the approved task committed, and
`.workflow/current/` reset. `/clear` when a genuinely fresh session is appropriate; `state.json` is what makes
that safe.

## Verification

**Check results, never declarations.**

A check that cannot come back false is decoration. Exit code 0 proves less than it appears to in this
ecosystem — piping to `tail` or `head` replaces a command's status with the pipe's, so a failed build reads
as success. Where an artifact should exist, test for the artifact.

"Configured" and "working" are different claims, and only the second is worth reporting. Say a route works
when a request returned 200. If you only verified the setup, say that.
